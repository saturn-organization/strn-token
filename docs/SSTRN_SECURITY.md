# sSTRN security and integration review map

Read [the concrete specification](SSTRN_SPEC.md) first. This is a built/tested candidate, not independent audit approval. Both tokens have committed ABI/storage baselines; compatibility checks do not establish semantic safety for arbitrary upgrades.

| Boundary                 | Control                                                                                                                        | Residual trust / audit focus                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| Principal versus rewards | Exact incoming/outgoing deltas; receipt supply is principal liability; excess recovery cannot spend backing                    | Reviewed STRN deployment and upgrades are trusted; no reward reserve or payout exists here                            |
| Restricted custody       | Deposits/renewals require STRN protection; funded protection cannot be removed                                                 | Governance must register the real proxy; code presence alone is not attestation                                       |
| Compliance seizure       | Move complete position and receipt into non-voting contract custody; underlying remains backed                                 | Authorized seizer remains trusted; release requires a separately administered RELEASER_ROLE with no per-release delay |
| Active versus mature     | Exact timestamp comparison, at most 32 positions per account, explicit owner renewal                                           | Chain timestamp bounds apply; no day rounding or keeper dependency                                                    |
| Withdrawal availability  | Local staking pause allows mature redemption; STRN restrictions still enforced atomically                                      | Underlying pause/blacklist can delay withdrawals; no emergency principal bypass                                       |
| Pause and utility        | Either staking or STRN pause returns zero discount; existing active time and votes remain                                      | Product policy must reflect this; pausing does not retroactively cancel seasonal points                               |
| Delegation               | Pinned OZ ERC20Votes/EIP712, timestamp checkpoints, nonces, owner/recipient blacklist checks; recovery custody cannot delegate | Previously delegated votes are not erased by blacklist; no deployed Governor/platform strategy here                   |
| Receipt transfer         | Public transfer/transferFrom/approve always revert; only privileged recovery and authorized release move ownership             | Wallet ownership itself cannot be made nontransferable by this contract                                               |
| Reentrancy               | Pinned stateless ReentrancyGuardTransient around all principal/position changes; CEI and rollback                              | Requires Cancun/EIP-1153 chain support; configured STRN must be authentic                                             |
| Upgrades                 | Atomic transparent initialization, locked implementation, independent sSTRN ERC-7201/ABI baselines, runtime fixture            | Timelock upgrades can change every policy; layout compatibility does not prove semantic safety                        |
| Fee discounts            | Exact 5,000-token threshold, integer BPS, 25% ceiling; floor savings when applied to full fee                                  | Getter does not enforce a spend cap; no production sUSDat integration is included                                     |

## External accounting boundary

Points and rewards require an external indexer and funded distributor. Principal is never reward funding. See [seasonal accounting](INTEGRATION_REQUIREMENTS.md#seasonal-accounting) and [points recovery](INTEGRATION_REQUIREMENTS.md#points-treatment-after-seizure) for event reconstruction, duplicate-claim prevention, case decisions and reorganization handling. These controls are not implemented by the token contracts.

## Static-analysis triage

The current deployment-scope analysis reports two medium `unused-return` findings, one in each token: `_checkpointRecovery` ignores the old/new values returned by OpenZeppelin `Checkpoints.push`. Those values are informational; `push` persists the checkpoint or reverts, and no success flag is ignored. This is reviewed as non-actionable; historical/same-timestamp/rollback tests verify the stored result. The findings are retained in raw analysis output rather than globally suppressed. Three low-severity timestamp findings identify deliberate exact-maturity checks, including mature release; no randomness or price decision is derived from timestamps. Two informational assembly findings identify fixed ERC-7201 slots in STRN and sSTRN. The informational STRN `_getVotingUnits` dead-code report is a virtual-dispatch false positive; inherited delegation exercises it in the mixed-balance tests. `CLOCK_MODE` naming is the ERC-6372 standard interface. Re-evaluate every fresh report; this is not a findings allowlist. Deployment authenticity, configured memberships, fee economics, offchain indexing and arbitrary future upgrades remain separate review concerns.

Sources guiding implementation: [pinned OpenZeppelin voting pattern](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20), [timestamp governance clocks](https://docs.openzeppelin.com/contracts/5.x/governance), and [Solidity security guidance](https://docs.soliditylang.org/en/latest/security-considerations.html). The checked-in dependency commits and compiler pin control this build, not later changes to those pages.

## Recovery custody and governance boundary

Recovered positions retain their original records with owner equal to the staking proxy. Their receipts remain outstanding on that proxy, without ordinary enumeration, voting, renewal or fee utility. No address may delegate as the proxy or to it. This uses the pinned ERC20Votes transfer path to remove old delegated weight while preserving total-supply checkpoints; no synthetic mint/burn or second principal ledger is used. Recovery checkpoints are an aggregate historical view of the proxy's receipt balance. Same-timestamp changes coalesce. Seizure does not retroactively invalidate an earlier voting snapshot.

Only RELEASER_ROLE may call `releasePosition`, immediately. Deployment grants it to the explicit release operator through the initial delayed role batch; default administration and ProxyAdmin ownership remain with the five-day timelock. SEIZER_ROLE, recovery-wallet ownership, changing the recovery address, and maturity grant no release power. Receipt release restores ordinary rights and obeys the recipient's 32-position bound. Mature underlying release burns the claim and pays the authorized recipient directly with exact balance checks. Both are explicit dispositions; underlying release ends recovery restrictions. STRN supplies liquid vote checkpoints; platform aggregation remains separate. An authorized release operator can intentionally release to an address it controls, so independent approval/accountability remains an operational requirement.

Token total-supply checkpoints include recovered supply, preserving principal accounting. The governance platform excludes historical recovered principal from its eligible-supply denominator at the same snapshot used for voting weight. An external Governor or offchain strategy must implement that subtraction and correctly combine liquid and staked supply without backing duplication. No Governor, emergency cancellation or retrospective ballot invalidation is implemented by this token. This platform policy can lower future quorum thresholds after seizures; it is an explicit governance consequence, not an onchain supply burn.
